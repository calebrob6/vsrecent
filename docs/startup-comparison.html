>_ VS Recent Startup architecture note

C# WinForms compared with Rust and raw Win32

Why the Rust build opens in about 70 milliseconds

The former self-contained .NET 9 application reached its first window in 359-390 ms during migration testing. The native Rust build reached it in 63-85 ms on the same machine. Two changes account for most of the gap: the process no longer boots a managed UI runtime, and history loading no longer blocks the first paint.

The rewrite reduced observed warm startup by roughly 4-6x and release size by about 200x.

Critical path

What must finish before pixels appear

The old implementation performs data access and model construction before a form exists. The current implementation creates and paints the picker first, then starts the same data work on a worker thread.

C# / .NET 9 / WinForms

359-390 ms
  1. Windows maps the native .NET app host.The host locates the embedded single-file bundle and prepares the runtime.
  2. CoreCLR starts.Runtime libraries, metadata, the GC, and managed execution support become available before Main.
  3. WinForms initializes.High-DPI mode, visual styles, application services, and framework types are activated.
  4. VS Code history loads synchronously.The UI thread opens SQLite, reads JSON, parses entries, classifies remotes, and creates search keys.
  5. MainForm constructs its managed control tree.Fonts, panels, controls, docking rules, event handlers, accessibility properties, and drawing state are allocated.
  6. Application.Run(form) creates handles and permits first paint.The user waits for every earlier step even though the history is not required to draw the shell.

Rust / native Win32

63-85 ms
  1. Windows maps a small native PE.There is no managed runtime, assembly graph, or GC to initialize.
  2. Minimal process setup runs.The app sets DPI awareness, initializes common controls, reads the theme, and claims a named mutex.
  3. The window class and state are created.A compact Rust state structure replaces the managed form object graph.
  4. Five native child controls are created.The edit, combo box, list box, footer, and separator are direct USER32/common-control windows.
  5. ShowWindow and UpdateWindow force first paint.The picker is visible with a loading row before any database call begins.
  6. History loads on a worker thread.SQLite, JSON parsing, classification, and search indexing run after first paint, then post results to the UI thread.

Where the time went

Four concrete differences

01

Managed runtime startup is gone

The C# executable is an app host plus a bundled .NET runtime and framework. CoreCLR must establish managed execution, load metadata, initialize the garbage collector, resolve assemblies, and prepare methods for execution. Framework libraries may contain precompiled code, but the application still crosses the host-to-runtime boundary and JIT-compiles application methods as needed. Rust produces native machine code ahead of time, so execution enters the program without CoreCLR.

02

The deployment image is about 200x smaller

The v0.4.0 self-contained executables were 50.4 MB for x64 and 49.6 MB for ARM64. The v0.5.0 Rust executables are 250 KB and 236 KB. Windows demand-pages executables, so startup does not read every byte. The smaller native image still gives the loader, filesystem cache, antivirus scanner, and bundle machinery far less material to inspect. The old compressed single-file configuration can also incur native extraction work, especially on a first launch.

03

WinForms builds a larger abstraction layer

The old constructor creates managed objects for the form, text box, combo box, custom list box, labels, panels, fonts, docking layout, event delegates, accessibility data, and owner drawing. WinForms later realizes native handles and runs layout before painting. The Rust program asks Win32 for the exact controls it needs and handles messages directly. It avoids much of the managed object and layout infrastructure.

04

Database work left the first-paint path

This scheduling change has the largest effect on perceived startup. C# calls LoadEntries() before constructing MainForm. Rust calls ShowWindow and UpdateWindow before spawning the loader thread. SQLite and JSON still take time, but the user sees and can orient to the picker while that work finishes. Time-to-content may depend on history size; time-to-window no longer does.

The key source-level change

The order of operations

Former C# startup, simplified
// Managed runtime is already running here.
Application.SetHighDpiMode(...);
Application.EnableVisualStyles();

entries = LoadEntries();
// SQLite read
// JSON parse
// remote classification
// search-key construction

using var form = new MainForm(entries);
Application.Run(form); // first paint comes later
Current Rust startup, simplified
SetProcessDpiAwarenessContext(...);
InitCommonControlsEx(...);

let window = CreateWindowExW(...);
create_controls(window);

ShowWindow(window, SW_SHOW);
UpdateWindow(window); // first paint now

std::thread::spawn(move || {
    let entries = load_entries();
    PostMessageW(window, WM_ENTRIES_LOADED, ...);
});

Packaging and loading

How file size affects startup

The self-contained .NET executable

PublishSingleFile, EnableCompressionInSingleFile, IncludeNativeLibrariesForSelfExtract, and --self-contained=true package the application, CoreCLR, native runtime components, WinForms, System.Drawing, JSON support, and supporting framework assemblies into one distributable file. The target machine needs no preinstalled .NET runtime, but each process must still bootstrap the embedded runtime. A first launch can also pay extraction and antivirus costs that warm measurements may hide.

The optimized Rust executable

The release profile uses LTO, one code-generation unit, size optimization, symbol stripping, and abort-on-panic. Rust and serde_json code are compiled into the PE, while UI, graphics, SQLite, shell, and windowing services come from Windows system DLLs. The operating system usually has many of those DLL pages cached already. The resulting release contains little unrelated startup code.

Reading the measurements

Warm startup favors repeatability

Warm runs answer the interaction question

The taskbar-launch workflow happens repeatedly during a workday. Warm measurements reduce disk and one-time extraction variance, making them useful for the question, "How quickly does the picker appear when I press Win+1 again?" The 359-390 ms and 63-85 ms ranges represent that workflow.

Cold runs can widen the difference

A cold reboot, empty filesystem cache, first single-file extraction, or fresh Defender scan adds machine-specific noise. The 50 MB .NET bundle exposes more bytes and components to those systems than the 250 KB native image. Cold-start tests are still valuable, but they need controlled reboot or cache procedures to be comparable.

First window and complete data are different metrics

The Rust design optimizes first paint. Its list can still show "Loading recent folders..." while the worker reads SQLite. A complete performance study would record both first-window time and entries-ready time. The UI feels immediate because only the first metric blocks visual feedback.

The current regression budget is measured

The release-polish branch adds single-instance activation and UI corrections. On native ARM64, 50 interleaved warm runs measured main at 66.18 ms median / 73.35 ms p95 and the branch at 66.99 ms / 74.84 ms. The 0.81 ms median increase is small enough to keep the interaction effectively unchanged.

Engineering tradeoff

The speed came with more manual UI code

WinForms supplied layout, events, control lifetime, accessibility integration, DPI behavior, and drawing abstractions. The Rust version owns those details through HWNDs, message dispatch, GDI resources, FFI boundaries, and explicit cleanup.

Language choice and architecture both matter

A Rust port that opened SQLite before creating its window would still feel slower than this implementation. A C# version could improve perceived speed by displaying an empty form first and loading history asynchronously. The native build also avoids CoreCLR and WinForms startup. The critical-path redesign is responsible for a large share of the user-visible improvement.
